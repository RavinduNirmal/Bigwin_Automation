# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Playwright + TypeScript E2E test suite for the **BigWin admin portal** (lottery back office, Next.js + MUI), covering Login (password + OTP), the **Lottery Type** module (sidebar Lottery → Lottery Type) and the **Lottery Brand** module (sidebar Lottery → Lottery Brand), each with create / edit / delete / search / table / navigation / Review→Approve tests. There is no application code here — only tests, page objects and reporting glue. There is no build step; Playwright transpiles TS on the fly. (The framework was ported from an earlier Grabbit Vending suite; the original files are archived outside the repo in `../Bigwin_Automation_grabbit_backup_2026-11-20.tar.gz`.)

## Commands

```bash
npm ci && npx playwright install --with-deps   # setup

npx playwright test                            # all tests (setup + chromium)
npx playwright test tests/e2e/lottery-type/lottery_type_create.spec.ts   # one file
npx playwright test -g "TC-LT-CR-002"          # one test by its TC id
npx playwright test lottery-type/ --headed --debug
npm run test:login | test:lottery-type | test:lottery-type:<create|edit|delete|search|table|nav|approval> | test:lottery-type:ci
npm run test:lottery-brand | test:lottery-brand:all | test:lottery-brand:<nav|create|edit|delete|search|table|approval|use|logs|a11y> | test:lottery-brand:ci
npm run test:lottery-draw | test:lottery-draw:all | test:lottery-draw:<nav|create|approval|search|table|view|actions|validation|security> | test:lottery-draw:ci   # all exclude @slow; prefer --workers=1 (each test creates real draws)
npm run test:lottery-draw:demo        # headed ~5 min demo: one draw through every stage
npm run test:lottery-draw:lifecycle   # SLOW (~20-40 min): In Play -> In Play Post Cutoff -> Completed
npm run test:dbf                      # unit tests of the ticket DBF service

npm run allure:serve                           # view allure-results
npm run test:allure -- <playwright args>       # run + fresh Allure report (ALLURE_NO_OPEN=1 to only generate)
npm run test:network-rerun -- <playwright args> # run, then re-run ONLY tests that failed due to the network

npm run check                                  # typecheck (tsc strict) + lint - run before committing
npx playwright show-report                     # view playwright-report
```

`test:lottery-type` runs **headed**. Passing `--reporter=…` on the CLI replaces the configured reporters, so Allure results are only written if `allure-playwright` is included.

Lint policy (`eslint.config.mjs`): **errors** are real bugs and must be fixed (un-awaited Playwright calls/assertions, floating promises, `test.only`, invalid `expect`); **warnings** are tracked debt (`waitForTimeout`, `networkidle`, conditionals in tests, `any`). `combinedTest` and `setup` are registered as test aliases, and helpers that assert internally are listed in `assertFunctionNames` - add new `expect…`/`…AndVerify` helpers there. Don't name a helper `expectX`-something that the plugin could mistake for `expect(...)` without listing it. Allure helpers (`TestHelper.initTest/attachText/step`, `AllureHelpers.*`) are async - always `await` them.

## Configuration & environment

- The root `playwright.config.ts` is the live config (an older commented-out version sits at its top; `config/playwright.config.ts` is a stale commented-out copy - ignore both).
- `config/global-setup.ts` reads `config/env/${TEST_ENV}.json` (`dev` | `staging` | `prod`, **default `dev`**) and sets `BASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_OTP`. Only `dev.json` is filled in (BigWin dev: `https://e763fesnjnk.dev.accelr.net`); staging/prod are empty templates and global setup fails fast if `baseURL`/credentials are missing. `dotenv` is never loaded, so `.env` is not used.
- **OTP:** BigWin login is email + password, then a 6-digit OTP in a "Verify OTP" dialog. The dev server has a bypass OTP (`123456`, in `dev.json`) - it actually accepts any 6 digits, so there is no "wrong OTP" test.
- `fullyParallel: false` keeps tests within a file in order; files run in parallel on several workers (2 on CI). Retries 0 locally, 1 on CI. `actionTimeout` 120s; specs use `describe.configure({ timeout: 180000 })` (login 240000 - the login API can be slow).
- Reporters: html, list, json (`test-results.json`), allure (`allure-results/`).
- **Windows gotcha:** a run hangs silently at "clear output" if another Playwright process (e.g. a paused Playwright-MCP/agent session or the VS Code test server) still holds files in `test-results/`. Stop that process (or its paused test) and re-run.

## Architecture

Layering: **spec → fixture → page object / modal → component → utils**.

- `pages/base.page.ts`: abstract `BasePage` (logger, `CustomWaits`, safe click/fill). `pages/lottery-type/lottery-type.page.ts` (`LotteryTypePage`) is the façade: it composes `components/` (Table, Search, Toast, Modal), lazily creates the Create/Edit modals, and owns high-level actions - `createLotteryType`, `editLotteryType`, `deleteLotteryType`, `openRowMenu`, `openLogs`, `searchLotteryTypes`, `selectTab`, `sortByColumn`, `getLotteryTypeData`, `verifyLotteryTypeData`. Specs call these, not raw locators.
- **App behaviour baked into the page object:** successful Create/Update/Delete end with `window.location.reload()` and show **no toast** (only delete toasts "Lottery type deleted successfuly"), so actions wait for the page `load` event and the table; failures show react-hot-toast messages (`role="status"`, e.g. "Failed to create lottery type"). Delete has **no confirmation dialog** and is a hard delete. The list API returns every record on one page, so CRUD helpers find a record by its code in the unfiltered table.
- **Approval workflow:** Create/Edit → Stage "Under Review" (Update dialog offers **Review**) → Review → "Pending Approval" (offers **Approve**) → Approve → "Approved" (neither). Editing an Approved record (Type or Status) sends it back to "Under Review". `lotteryTypePage.reviewLotteryType/approveLotteryType` + `utils/helpers/lottery-type/approval.helpers.ts` (`expectApprovalStage`, `createApprovedLotteryType`, `expectOfferedForUse`). "Ready for use" is checked READ-ONLY in Lottery Brand > Add New Brand > "Select Lottery Type" (`pages/lottery-brand/lottery-brand-form.page.ts`, fixture `lotteryBrandFormPage`) - never submit that form. Spec: `lottery_type_approval.spec.ts` (`TC-LT-APR-*`).
- **Lottery Brand** (`pages/lottery-brand/`, fixtures `lotteryBrandListPage`, `addBrandWizardPage`, `lotteryBrandDetailPage`, `createDrawPage`; data `testLotteryBrandData` from `fixtures/lottery-brand-data.fixture.ts`, codes `ATB…`; helpers `utils/helpers/lottery-brand/`; specs `tests/e2e/lottery-brand/` = `TC-LB-*`, metadata split per spec: `data/metadata/lottery-brand/{nav,create,edit,delete,search,table,approval,use,logs,a11y}.metadata.ts`, built with `brandCases()` from `lottery-brand/base.ts` (verified ACTUAL results of known defects in `actualResult`), from `specs/lottery-brand-test-plan.md`). Differences from Lottery Type: the list API honours search/sort/tabs/paging (find your brand by searching its code); Add New Brand is a 4-step wizard and the brand is created at Step 3 "Add Brand"; the brand page (`edit-lottery-brand?lotteryId=`) has view mode (Review / Approve / Update) and edit mode ("Update" → Save Changes); delete is a **soft delete** (brand moves to the Deleted tab forever - every run leaves its `ATB…` brands there). "Ready for use" = offered in **Create Draw > Lottery Brand** (read-only, never create a draw).
- **Lottery Draws** (sidebar Lottery Draws → Draws, `/dashboard/draw`; `pages/draw/` = `LotteryDrawListPage`, `CreateDrawPage`, `LotteryDrawDetailPage`; data `testLotteryDrawData` in `fixtures/lottery-draw-data.fixture.ts`; helpers `utils/helpers/lottery-draw/`; specs `tests/e2e/lottery-draw/` = `TC-LD-*`; metadata split per spec: `data/metadata/lottery-draw/{nav,create,approval,lifecycle,search,table,view,actions,validation,security}.metadata.ts` + `lottery-draw/ticket-dbf.metadata.ts`, built with `drawCases()` from `lottery-draw/base.ts` (Objective, Preconditions, Test Data, Steps, Expected, `actualResult` for known defects, Postconditions); plan `specs/lottery-draw-test-plan.md`). Create Draw = Step 1 details (brand, number, code, issue start / cutoff / draw date-times, mega prize; Next asks a native confirm) → Step 2 upload (Select File → "Upload Files" dialog → Add, MD5 Checksum, Initiate Now) → Create Draw. Stages (tabs): Under Review → **Review Draw** → Pending Approval → **Approve Draw** (dialog needs the upload's MD5; a wrong MD5 → 400 "Invalid MD5 checksum") → Approved → In Play (at issue start) → In Play Post Cutoff (at cutoff) → Completed (at draw date); also On Hold, Rejected, Deleted. Tickets load in the background - Review is refused ("This draw has no tickets…") until they have, so `reviewDrawAndVerify` waits via `waitForTicketsLoaded`. **Draws cannot be deleted**: test draws use draw numbers `9xxxxxxxxx`, codes `AT9xxxxxxxxx`, far-future schedules (never go In Play) and afterEach **rejects** own leftovers that are still Under Review / Pending Approval. Only the `@slow` lifecycle test uses imminent times.
- **Ticket DBF service** `utils/dbf/ticket-dbf.service.ts`: Node port of `utils/dbf_ticket_generator.html` - `writeTicketDbf({ startId, totalRecords, prefix: '0', numbersPerRecord: 4, seed? }, outDir, name)` → `{ filePath, md5, firstBarcode, lastBarcode }`. Same dBASE layout as the HTML tool (BARCODE C14, SYMBOL C7, LETTERS C7, NUMBERS C35), verified by `tests/unit/ticket-dbf.service.spec.ts` (`TC-DBF-*`). Barcode = prefix + sequence (max 14 chars). Letters/numbers are random (pass `seed` for reproducible files/MD5).
- `pages/auth/login.page.ts` + `otp.modal.ts`: `login(email, pw)` does step 1; `loginWithOtp(...)` does both. `OtpModal.submitOtp` accepts the native `alert("Successfully validated OTP")` and keeps its text in `lastAlertMessage`.
- **Auth is a setup project.** `tests/auth.setup.ts` (project `setup`, which `chromium` depends on) logs in once per run with password + OTP and saves `storageState` to `playwright/.auth/admin.json` (git-ignored). BigWin keeps its session in **localStorage** (`accesstoken`, `tokenExpiry` ~8h, `userId`), which storageState captures, so no extra session handling is needed. `--no-deps` skips setup and reuses the last saved session.
- `fixtures/auth.fixture.ts`: exports the `test`/`expect` specs use. `authenticatedPage` opens `/` with the saved session, fails fast on 401/403 or if the login form appears, clicks the real sidebar (Lottery → Lottery Type) and yields `{ page, loginPage, lotteryTypePage }`. Login-page tests opt out: `test.use({ restoreSession: false, storageState: { cookies: [], origins: [] } })`.
- `fixtures/lottery-type-data.fixture.ts` → `data/factories/lottery-type-data.factory.ts`: `testLotteryTypeData` gives `unique(status)`, `withCode/withName`, `newCode/newName`, `invalid.*`, `security.*`, `edge.*`, `taggedSet(n)`. Every generated code starts with **`AT`**. Specs merge it with the auth fixture: `mergeTests(test, dataTest)` → `combinedTest`.
- **Allure metadata is keyed by test ID** and lives in one folder per module: `data/metadata/{login,lottery-type,lottery-brand,lottery-draw}/` (the ticket DBF unit tests belong to `lottery-draw/`). Each folder has an `index.ts` that merges its `*.metadata.ts` files and exports `register<Module>Metadata()` (`registerLoginMetadata`, `registerLotteryTypeMetadata`, `registerLotteryBrandMetadata`, `registerLotteryDrawMetadata`). Each spec calls its module's register function at the top (e.g. `import { registerLotteryDrawMetadata } from '../../../data/metadata/lottery-draw'`); each test calls `await TestHelper.initTest('<TC-ID>', page)`, which throws if the id has no entry. `data/metadata/index.ts` merges all modules (`AllTestMetadata`, `registerAllMetadata()`) for tooling. New test → add an entry with the same id to its module's `*.metadata.ts`; new metadata file → add it to that module's `index.ts`; new module → new folder + add it to the root `index.ts`. Use `TestHelper.step/attachText`, `AllureHelpers.attachScreenshot`, end with `TestHelper.success(...)`.
- **Reusable helpers live in `utils/helpers/`**, never in specs. `utils/helpers/lottery-type/` is split by concern (`create`, `edit`, `delete`, `search`, `table`, `sort`, `cleanup`) and re-exported from `index.ts`; app-wide helpers (`TestHelper`, `Helpers`, toast helpers) are in `utils/helpers/common/`.
- **Locators are user-facing** (`getByRole`/`getByText`) and live only in page objects/components. Documented exceptions: the Status MUI select (`[aria-haspopup="listbox"]`) and the Stage input (`input[name="approvalstatus"]`) in `lottery-type-form.fields.ts` because their labels aren't associated; the row-actions icon button has no name (`rowFor(code).getByRole('button').last()`); the OTP dialog has no accessible name (found by its "Verify OTP" text); `renderedMarkupIn(code)` is a CSS check that HTML is not rendered. Toasts use `getByRole('status', { includeHidden: true })` because an open dialog marks the page `aria-hidden`.
- **Network rerun:** `fixtures/network-monitor.fixture.ts` is an auto fixture inside `auth.fixture`'s `test`. When a test finally fails AND there is network evidence (`net::ERR_*` other than ABORTED, 502/503/504, a request slower than `NETWORK_SLOW_MS` (20s) or stalled, network error in the message), it records the test in `playwright/.network-rerun/`. `scripts/run-with-network-rerun.js` re-runs only those after `NETWORK_RERUN_DELAY` (30s) with 1 worker (reports in `*-rerun<N>`), writes `network-rerun-summary.json`. Real failures keep exit code 1. Tests that cut the network on purpose need `{ tag: '@simulated-network' }`; `SIMULATE_NETWORK_FAILURE=<TC id>` forces API timeouts for a demo. Note the app polls notifications every 30s.
- **Parallel-safe data rule:** workers share one live dev database (other people use it too), so never assert on "the first row", total counts or the whole table's contents. Assert on the test's OWN uniquely coded records (`expectLotteryTypeInTable/NotInTable`, `expectRowCountForCode`, `expectLotteryTypeSaved`) or on properties that hold regardless of other rows (sort order). Each test records submitted codes in `LotteryTypeCreateModal.submittedCodes` and `afterEach` calls `cleanupLotteryTypes`, which **only deletes codes starting with `AT`** - never submit a real code (e.g. `PASS`) other than through that guard. **Review/Approve** (maker-checker) may only be clicked on the test's own `AT…` records - never on anyone else's.
- Test conventions: titles start with the TC id (`'TC-LT-CR-002: …'`; ids `TC-LOGIN-*`, `TC-LT-NAV/CR/ED/DEL/SRCH/TBL/APR-*`). Specs use `describe.configure({ mode: 'default' })`.
- A failing test is a result: if the app misbehaves, the test must fail with a clear message - never `fixme`/skip it or weaken the assertion. Known app defects the suite currently reports (as of 2026-11-22; each failing draw test's metadata has an `actualResult`): Draws - draw creation intermittently fails with 400 "Error occured while creating draw with code …" (backend, even on 1 worker); Create Draw: Back from Step 2 clears the Lottery Brand (CR-011), Step 2 "Brand Name" sometimes empty (CR-003), same brand accepts two draws at the same draw time (CR-013), cancelling the confirm still opens Step 2 (CR-016), "darw" typo (CR-017), the confirm is asked BEFORE validation (VAL-001); validation does not block cutoff = start (VAL-002), cutoff = draw date (VAL-004), past dates (VAL-005, LC-002), 20-digit draw number / 21-digit mega prize (VAL-009/012), spaces-only or 300-char code (VAL-013/014), stale cutoff error (VAL-006), non-DBF files (VAL-016), DBF barcodes of another draw number (VAL-018); list: empty search shows no message (SRCH-005), "%" matches everything (SRCH-008), search not trimmed (SRCH-009), Draw Code sort not ordered (TBL-006), column chips not persisted (TBL-011); actions: Add Tickets without a file closes the dialog (ACT-004), Add Tickets never registers the upload (ACT-005), Remove Draw makes the draw vanish from every tab incl. Deleted (ACT-007); draw page: title "Foundation: Blank Page | Carpatin" (NAV-010), "Winnning" typo (VIEW-004), send-back logged as "rejection is approved" (APR-008), unknown drawId shows an empty page (SEC-003). Draw app facts the page objects rely on: Pending Approval "Reject" = PUT /api/draw/approve-reject/{id} and returns the draw to Under Review (cleanup rejects twice); Hold/Activate = ticket-service PUT lottery-draw/toggle-hold/{id}/1|0; Remove Draw asks to type the draw code; clicking an already-selected tab sends no request (`selectTab` skips it). Lottery Type search, sorting and the Active/Deleted tabs do nothing (the list API ignores query/sort/view); no tab is selected on load; Create ignores Status DISABLED (saved as ACTIVE; Edit saves it correctly); a Type of only spaces is accepted; changing a Code to an existing one fails silently (no error shown); unapproved lottery types (Under Review / Pending Approval) are offered in Lottery Brand > Select Lottery Type (APR-004/005/010); row menu "Logs" opens a 404 page `/dashboard/audit-log` (NAV-005). The verified test plan with more findings is `specs/lottery-type-test-plan.md`.

## AI test agents

Playwright Test Agents (`playwright-test-planner`, `-generator`, `-healer`) drive the Playwright test MCP server (`npx playwright run-test-mcp-server`):
- **Claude Code:** `.claude/agents/*.md` + `.mcp.json`. Each agent file ends with a **PROJECT RULES** section (BigWin conventions + never hide an app bug). Re-running `npx playwright init-agents` overwrites these files - re-append the rules.
- **GitHub Copilot:** `.github/agents/*.agent.md` + `.vscode/mcp.json`.

`tests/seed.spec.ts` uses `authenticatedPage`, so agents start logged in on Lottery Type. The planner writes plans to `specs/`; `.playwright-mcp/` holds session logs. A paused agent session keeps a worker alive - stop it before normal runs (see the Windows gotcha above).

## CI

`.github/workflows/playwright.yml` runs `npx playwright test` on push/PR to `main`/`master` and uploads `playwright-report/`. CI needs network access to the BigWin dev server.
